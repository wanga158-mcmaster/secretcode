# frontier: one formal representation per organization

Sixteen bots (`frontier/<bot>`), each a complete team organization built on a different formal
representation from operations research, scheduling, control or game theory.

## Doctrine

**Question.** Does changing the *representation* of the team's production problem, rather than
the value of a job inside a shared planner, let a team earn, own and convert capability into
score in ways a shared estimator never attempts?

**Shared hypothesis.** The economic unit is an executable multi-actor program: who clears, who
holds the capture, who banks, who buys what, and in which (round, phase, slot). Camps are timed
joint processes whose damage, kill, payout and score are different events; gold, bags and
observations are personal; moves, casts, cooldowns and initiative are discrete precedence
constraints; fuel is an execution resource. A card that represents one such structure
explicitly should find organizations that coarse shared models cannot express. Each card is a
hypothesis to keep or reject, not a promised winner.

**Held fixed (`common/`).** SDK legality and the private-observation contract, terrain routing,
lifecycle execution with the turn-boundary catch/log/yield, bounded physical work primitives,
economic receipts, capital/shop plumbing, the fuel guard and integer trace logging. `common/`
supplies no source ranking, admission rule, purchase menu, roster or value function.

**Varied per bot.** Roster (five-pick draft order), state representation and model, decision
procedure and horizon, capital menu and thresholds, cold start and productive fallback, and the
card's own same-roster control (`p10::Arm::control`).

**Not the neighbours.** commitments and models vary a thin overlay or a forecaster on one shared
ranker; decision and events vary a decision or valuation rule over a shared job menu; doctrines
anchors economic doctrines on champion mechanics; specialists forks B0 with one mechanism;
adaptive gates commitments on private completed episodes; territory varies geography;
distributed varies message-free coordination. Here the decision procedure, roster and executed
program all differ per bot. Frontier work never adds a shared scorer, picks each roster as part
of its card's hypothesis, and rejects a card that reduces to a neighbour's mechanism: 16 is not
bounty or high-bag targeting (doctrines' Privateer idea), 06 not an individual reset trick
(specialists/domino), 02 not one actor's shield continuation (doctrines/collateral), 14 not
compact linked-pair survival (doctrines' Labor Surge idea), 03 not a one-time role split
(adaptive/assay-guild), 09 not an isolated Ren hook (specialists/porcupine).

## Distinctness rules

- A bot counts only if, in some reachable state, its rule executes a different program (roster,
  assignment, owner, purchase or timing) than every other frontier bot and than its own
  `Arm::control`. Two bots that make the same choices count as one: redesign or merge them.
  03 and 06 share a roster, so their difference must stay in the executed program.
- Each card keeps a discriminating fixture: a positive state where active and control choose
  different legal programs, a negative state where the feature is refused, and an invalidated
  forecast. Banked gems never certify a mechanism; the card's own event (handoff, reset stock
  use, denied substitute, ...) must appear in a capture-bank-renew trace.
- `common/` stays mechanical. Source ranking, admission, purchases and rosters belong in the
  card; never move one card's working mechanism into `common/` to lift the others.
- Keep two or three structural alternatives per card (idea bank below) instead of collapsing
  the suite on one local optimum; tune parameters only after the mechanism works.
- One owner edits `common/` at a time. A shared change affects all 16 bots: rebuild with
  `arena build frontier` and rerun the whole `arena test frontier`. Card files belong to whoever
  develops that card; cross-card fixtures (`cards-*`, `c-capital-ownership`) rerun on any change.

## Layout and checks

- `<bot>/src/main.cpp` runs `p10::run<CPolicy>(profile, p10::Arm::active)`; the runtime loop
  catches engine exceptions each turn, logs `p10 error [...]` and yields.
- `<bot>/src/`: `model.h` (card representation), `policy.h` (A: profile and first
  organization), `b-policy.h` (B: movement-aware layer), `c-policy.h` (C: live layer with its own
  capital menu), plus card headers (`search.h`, `wave.h`, `local-pair.h`,
  `independent-tactics.h`). Cards 06-16 build C on B. For 01-05, C uses the card model and A only
  supplies the profile; their B layers are not in the live build but stay under test.
- `common/src/`: `sdk.h` (pinned SDK ABI reads, legality masks), `contract.h` (World, Directive,
  Profile, Arm, receipts), `navigation.h` (routing fields), `runtime.h` (turn loop, observation,
  execution, fuel gates), `physical-turn.h`, `physical-appointments.h`, `combat.h`,
  `partial-work.h`, `mobile-work.h` (bounded physical work), `economic-observation.h`,
  `c-capital-{01-05,06-10,11-16}.h` (receipt and shop plumbing), `guard.h` (round/fuel guard,
  action reserve), `trace.h` (integer-only logs).
- Fuel: actions reserve max(41000, 40% of entry); inspect/move max(38000, 93% of that), 38,130 at
  100k. A completed action has cost 42,588, so 41k is a floor: keep the inner round/fuel guards.
- `p10` is the code identifier: `p10::`, slugs `p10-<bot>`, fixtures `tests/plan10-*` and the
  `p10 decision|phase|witnessed|error ...` log lines that the analyzer parses.
- Build: `./arena.cmd build frontier`. Test: `./arena.cmd test frontier`, or
  `./arena.cmd test frontier -- [bot ...] [--case NAME] [--list]`: 19 WASI fixtures,
  `native-executor` (a generated public-access copy of `runtime.h` executing against fail-closed
  SDK mocks in `plan10-native-executor.mjs`, both arms), 16 strict `-Wall -Wextra -Werror`
  syntax checks and the analyzer unit tests. Bot names select the cases whose includes reach that
  bot; shared-module and tool cases run in the whole-suite run.
- `tools/analyze_native.py OUTDIR --candidate-side A|B --bot NAME [--output FILE]`: read-only
  diagnostics of one `cambc run` output directory (statistics.json plus a replay): purchases,
  payouts, submissions, fuel exhaustion, faults, `p10` log records and prediction timing.
